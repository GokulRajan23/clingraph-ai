ClinGraph AI — Implementation Plan

Phase-by-phase hackathon roadmap • 12 November 2026 • Proposed plan, not implemented

MVP: Upload 5–6 German-language reports for one synthetic patient → extract clinical events → connect observations across dates → display a timeline → answer patient-history questions with clickable source evidence. Keep the architecture disease-independent.

Interface: Uploaded reports on the left; clinical timeline in the centre; patient-history chatbot and source-evidence tab on the right.

Phase 1 — Define the demo and reference answers

  • Prepare synthetic reports with a finding first documented, progressing and becoming stable; another finding improving; a complication; and a procedure.
  • Include negated and suspected findings, missing dates and contradictory statements.
  • Manually label expected events, exact evidence sentences and links between observations. Seek clinician review where available.
  • Prepare 15–20 questions and expected answers, including unanswerable questions.
  • Reserve separate patient cases for final evaluation.

Complete when: A versioned sample dataset, event schema, reference annotations and question set exist.

Phase 2 — Report upload and document viewer

  • Build PDF/text upload, report list and processing-status display.
  • Extract text with Docling; use OCR for scanned documents.
  • Preserve report ID, page number and source coordinates or text offsets.
  • Extract dates with explicit date types and allow correction; distinguish report date from clinical event date.
  • Display original documents and extracted text. Handle unreadable files and duplicates.

Complete when: All demo reports are readable, correctly organised by date and openable in the viewer; failed processing is visible.

Phase 3 — Benchmark and select the clinical extraction model

  • Compare a general-purpose Qwen candidate with a medically adapted candidate whose German-language capability can be tested. Neither model category guarantees clinical correctness.
  • Use the same clinician-reviewed German examples, event schema and scoring rules. Include abbreviations, negation, uncertainty, historical findings, anatomy, units and explicit comparisons across dates.
  • Separate development, model-selection and final evaluation patient cases. Do not tune prompts or choose models using the final test set.
  • Measure event precision/recall, serious interpretation errors, citation support, missing-evidence handling, latency and hardware requirements. Check model licensing and deployment suitability before choosing.
  • Record model version, prompt version and inference settings. Select a model only after reviewing measured errors; otherwise narrow the supported task and repeat the benchmark.
  • Use a replaceable model interface. Consider fine-tuning later only if recurring errors justify it and enough reviewed training data exists.

Complete when: A comparison scorecard and error review justify the selected model and its supported scope. Without clinician-reviewed examples, label this a preliminary technical benchmark, not clinical validation.

Phase 4 — Extract clinical events with evidence

  • Use the benchmark-selected, version-pinned model to propose schema-constrained event records; validate with Pydantic. Qwen is a candidate, not a required dependency.
  • Capture finding, category, anatomy/laterality, assertion, event date, report date, change status, evidence and review status.
  • Verify quoted evidence against the extracted report text and retain source locations.
  • Preserve uncertainty and unknown values. Restrict the MVP to changes explicitly documented in the reports; do not infer disease progression from measurements alone. Otherwise show change unclear or require review. Valid JSON and a genuine citation do not prove correct clinical interpretation.
  • Evaluate German negation, uncertainty and section handling explicitly. Use a clinician-reviewed German terminology and rule layer for abbreviations, synonyms, negation, uncertainty, anatomy and units. Retain original wording and measure whether each rule improves results.

Complete when: Extraction is checked against labelled examples, including negation and uncertainty, and every displayed event has traceable evidence.

Phase 5 — Link findings across reports

  • Generate candidate links using finding terminology, anatomy, laterality, measurements and explicit comparisons.
  • Connect observations belonging to the same finding; retain the evidence and reasoning for each link.
  • Represent findings, dated observations and relationships in database tables.
  • Keep ambiguous matches separate or flag them for review.
  • Preserve the comparison date stated in each report, even when it is not the most recent report.

Rules: First documented ≠ onset. Not mentioned ≠ resolved. Device present ≠ device placed on the report date. Similar wording ≠ the same anatomical finding.

Complete when: Expected event chains are reconstructed without merging unrelated findings; uncertain links can be reviewed.

Phase 6 — Interactive timeline and corrections

  • Show separate rows for findings and dated cards for observations.
  • Use colour plus text for first documented, progressed, stable, improved and procedure events.
  • Add category/date filters and event selection.
  • Open the source sentence and original page from each event.
  • Allow users to confirm or correct events and reject incorrect links; preserve the original extraction and correction history.

Complete when: Users can follow changes, verify sources and correct the timeline.

Phase 7 — Patient-history chatbot

  • Retrieve patient-specific evidence before generating answers.
  • Provide bounded tools: search reports, retrieve a finding’s observations, filter by date and open source passages.
  • Use both structured events and original text; retrieve the complete relevant sequence for longitudinal questions.
  • Attach clickable source citations to factual claims and verify that the passages support the intended meaning. Retrieval cannot compensate for incorrect interpretation. Flag missing or conflicting evidence and avoid unsupported diagnostic or treatment conclusions.
  • Keep retrieval strictly scoped to the selected patient. Treat report contents as data, not instructions.
  • Keep corrected timeline data and chatbot retrieval consistent.

Example questions: “What changed between these reports?” “When was this finding first documented?” “Which procedures are documented?” “What information is missing?”

Complete when: The fixed question set has been evaluated for accuracy, completeness, citation support and appropriate handling of unanswerable questions.

Phase 8 — Evaluation, polish and demo

  • Measure event precision/recall, link precision/recall, temporal correctness and citation support.
  • Evaluate chat correctness and missing-evidence handling on unseen patient cases.
  • Compare task time and answer accuracy with original reports versus ClinGraph; include source-verification time.
  • Test duplicates, unreadable PDFs, contradictory reports, failed model requests and patient separation.
  • Prepare a repeatable demo and a clearly labelled preprocessed fallback if live inference is unavailable.
  • Report actual results and denominators; do not claim clinical validation from a small synthetic dataset.

Complete when: The complete workflow is reproducible, the evaluation is recorded and the demonstration has a clear evidence-backed story.

Proposed technical stack

LayerInitial choice
InterfaceReact + TypeScript
BackendPython + FastAPI
PDF/text extractionDocling, with OCR where needed
Language modelReplaceable, benchmark-selected model; compare Qwen and a medically adapted candidate on German reports before selection
ValidationPydantic schemas, source-text/date/unit checks, German clinical rules and clinician-reviewed evaluation
StorageSQLite and local files for the single-user demo
RetrievalPatient-filtered text search and structured event queries; add vector retrieval if evaluation justifies it
ServingHosted model endpoint for synthetic data, or local serving such as vLLM with suitable hardware

Current tooling notes and sources

  • Docling provenance support helps preserve references to original document locations.
  • vLLM structured outputs supports schema-constrained generation; factual validation remains necessary.
  • medSpaCy language support currently lists no supplied German ConText or section rules. Treat medSpaCy as optional infrastructure for custom German rules, not ready-made German clinical extraction.

Scope discipline: Start with synthetic data, benchmark model candidates, then use one selected model and an explicit processing pipeline. A dedicated graph database, multiple autonomous agents, hospital integrations and production deployment are later decisions. The immediate objective is a reliable, traceable hackathon prototype.
