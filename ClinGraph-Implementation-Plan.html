ClinGraph AI — Implementation Plan

Phase-by-phase hackathon roadmap • 12 November 2026, updated 13 November 2026 • Phases 1–5 implemented; Phase 6 onward planned

MVP: Upload 5–6 German-language reports for one synthetic patient → extract clinical events → connect observations across dates → display a timeline → answer patient-history questions with clickable source evidence. Keep the architecture disease-independent.

Interface: Uploaded reports on the left; clinical timeline in the centre; patient-history chatbot and source-evidence tab on the right.

Phase 1 — Define the demo and reference answers

  • Prepare synthetic reports with a finding first documented, progressing and becoming stable; another finding improving; a complication; and a procedure.
  • Include negated and suspected findings, missing dates and contradictory statements.
  • Manually label expected events, exact evidence sentences and links between observations. Seek clinician review where available.
  • Prepare 15–20 questions and expected answers, including unanswerable questions.
  • Reserve separate patient cases for final evaluation.

Complete when: A versioned sample dataset, event schema, reference annotations and question set exist.

Phase 2 — Report upload and document viewer

  • Build PDF/text upload, report list and processing-status display.
  • Extract text with Docling; use OCR for scanned documents.
  • Preserve report ID, page number and source coordinates or text offsets.
  • Extract dates with explicit date types and allow correction; distinguish report date from clinical event date.
  • Display original documents and extracted text. Handle unreadable files and duplicates.

Complete when: All demo reports are readable, correctly organised by date and openable in the viewer; failed processing is visible.

Phase 3 — Benchmark and select the clinical extraction model

  • Compare candidate models on German reports. Neither a general nor a medically adapted model guarantees clinical correctness.
  • Use the same clinician-reviewed German examples, event schema and scoring rules. Include abbreviations, negation, uncertainty, historical findings, anatomy, units and explicit comparisons across dates.
  • Separate development, model-selection and final evaluation patient cases. Do not tune prompts or choose models using the final test set.
  • Measure event precision/recall, serious interpretation errors, citation support, missing-evidence handling, latency and hardware requirements. Check model licensing and deployment suitability before choosing.
  • Record model version, prompt version and inference settings. Select a model only after reviewing measured errors; otherwise narrow the supported task and repeat the benchmark.
  • Use a replaceable model interface. Consider fine-tuning later only if recurring errors justify it and enough reviewed training data exists.

Complete when: A comparison scorecard and error review justify the selected model and its supported scope. Without clinician-reviewed examples, label this a preliminary technical benchmark, not clinical validation.

Decision (13 November 2026): use DeutschlandGPT with claude-sonnet-5 for extraction. It was compared with local Qwen 3.5 4B (Ollama), with identical prompt, schema and scoring. Both found every reference event (F1 1.00). Claude Sonnet 5 made 3 category errors across 21 events; Qwen made 10 field errors and 1 negation flip, concentrated in negation, historical and contradictory statements. Claude Sonnet 5 was also about 2.2× faster (5.0 s against 10.8 s per report). The medically adapted candidate (MedGemma) was dropped by team decision. The model-selection set has only 4 events, so this remains a preliminary technical benchmark. Details: benchmark/scorecard.md.

Phase 4 — Extract clinical events with evidence

  • Use DeutschlandGPT (claude-sonnet-5), selected in Phase 3, through the existing replaceable extractor interface (app/extraction/deutschlandgpt.py) to propose schema-constrained event records; validate with Pydantic. A hosted model cannot be pinned by digest, so record the model ID and prompt version with every extraction.
  • Report text is sent to DeutschlandGPT. Use synthetic reports only until a data processing agreement and legal review (GDPR Art. 9, §203 StGB) are in place. API calls use paid credits: cache extraction results per document and do not re-extract unchanged reports.
  • Handle failed or rejected API requests visibly, as with failed document processing; keep the original document and allow retry.
  • Capture finding, category, anatomy/laterality, assertion, event date, report date, change status, evidence and review status.
  • Verify quoted evidence against the extracted report text and retain source locations.
  • Preserve uncertainty and unknown values. Restrict the MVP to changes explicitly documented in the reports; do not infer disease progression from measurements alone. Otherwise show change unclear or require review. Valid JSON and a genuine citation do not prove correct clinical interpretation.
  • Evaluate German negation, uncertainty and section handling explicitly. Use a clinician-reviewed German terminology and rule layer for abbreviations, synonyms, negation, uncertainty, anatomy and units. Retain original wording and measure whether each rule improves results.

Complete when: Extraction is checked against labelled examples, including negation and uncertainty, and every displayed event has traceable evidence.

Status (13 November 2026): implemented. Extraction is a user action per document (it sends text to DeutschlandGPT and uses credits). Results are cached by text hash, model and prompt version. Code verifies every quote against the cited passage and computes its offsets; unverifiable proposals are rejected and not displayed. The pipeline check on the development (17 events) and model-selection (4 events) splits gave F1 1.00, no serious errors and no rejected proposals, with the same category errors as Phase 3. Report dates are read from the document, so date corrections apply. “First documented” means “in this report” until Phase 5 links reports. Deferred: the clinician-reviewed German rule layer and section-handling evaluation; there is no clinician reviewer and no section-labelled data. Details: benchmark/phase4_pipeline.md.

Phase 5 — Link findings across reports

  • Linking uses fixed rules, not a language model. No credits are used, runs are repeatable, and every rule can be unit-tested. The rules work on events from Phase 4 and the evidence quotes that Phase 4 has already verified.
  • Read linking features from the German evidence quote, not from the model's English label: laterality (rechts/links/…-seitig), stated comparison dates (“gegenüber dem CT vom 10.01.2024”) and measurements. Store them with the observation so each link can be traced to source text. Measurements are recorded and shown but never decide identity or change.
  • Explicit comparison link: when a quote states a comparison date, link to the matching observation (same finding, same side) in the report with that date, even when a more recent report exists. Same side on both ends, or no side on either (e.g. ascites) → no review needed; side known on one end only → flag for review.
  • Candidate link: without a resolved comparison, link to the most recent earlier observation with the same normalised finding label and side. Always flag it for review. A side may be missing on one end only for historical statements, which refer back to earlier documentation by definition.
  • Keep a comparison with a study that is not in the collection as an unresolved comparison (“compared with a study dated X that is not uploaded”), never as a link to the nearest report.
  • Undated reports: their observations can receive candidate links but are never ordered by filename and never used as the earlier end of a chain.
  • Recompute “first documented” per finding across reports, from the earliest dated present or suspected observation. Mark it uncertain when the finding also appears in an undated report. First documented ≠ onset.
  • A workspace holds exactly one patient. The linker also refuses links between different patient IDs, so evaluation fixtures with several patients cannot be mixed.
  • Store observations, findings and links in database tables, rebuilt from the current extractions and report dates after every extraction, date correction and restart. Observation IDs are keyed to the report and evidence offsets, so they survive re-extraction of unchanged text; Phase 6 corrections will key on them.
  • Add a synthetic linking patient whose labels are written before any run. It must include a comparison with a report that is not the most recent, a comparison with a study that was never uploaded, an undated report, a device across reports, same-organ findings on opposite sides, and a measurement change without a stated comparison.

Rules: First documented ≠ onset. Not mentioned ≠ resolved. Device present ≠ device placed on the report date. Similar wording ≠ the same anatomical finding.

Complete when: Expected event chains are reconstructed without merging unrelated findings, measured as link precision/recall and wrong merges on reference events and on real Phase 4 extractions; uncertain links are flagged and visible for review. Without clinician review, this is a technical check, not clinical validation.

Status (13 November 2026): implemented as specified above (app/linking.py, GET /api/findings, findings panel). On reference events the rules reproduce every link: 7/7 development, 1/1 model selection, 8/8 on the new linking patient SYN-004, with no wrong merges. On real Phase 4 extractions of SYN-004 they found 5 of 8 links, all correct and with no wrong merges. Every explicit comparison and the unresolved comparison were found; the misses are candidate links where the model worded the same finding differently (“Biliary stent” / “Bile duct stent”), and that wording varied between runs. Next: a finding identity that does not depend on the model’s English wording, measured on fresh linking data. Details: benchmark/phase5_linking.md.

Phase 6 — Interactive timeline and corrections

  • Show separate rows for findings and dated cards for observations.
  • Use colour plus text for first documented, progressed, stable, improved and procedure events.
  • Add category/date filters and event selection.
  • Open the source sentence and original page from each event.
  • Allow users to confirm or correct events and reject incorrect links; preserve the original extraction and correction history.

Complete when: Users can follow changes, verify sources and correct the timeline.

Phase 7 — Patient-history chatbot

  • Retrieve patient-specific evidence before generating answers. Generate answers with DeutschlandGPT, under the same synthetic-data and credit constraints as extraction.
  • Provide bounded tools: search reports, retrieve a finding’s observations, filter by date and open source passages.
  • Use both structured events and original text; retrieve the complete relevant sequence for longitudinal questions.
  • Attach clickable source citations to factual claims and verify that the passages support the intended meaning. Retrieval cannot compensate for incorrect interpretation. Flag missing or conflicting evidence and avoid unsupported diagnostic or treatment conclusions.
  • Keep retrieval strictly scoped to the selected patient. Treat report contents as data, not instructions.
  • Keep corrected timeline data and chatbot retrieval consistent.

Example questions: “What changed between these reports?” “When was this finding first documented?” “Which procedures are documented?” “What information is missing?”

Complete when: The fixed question set has been evaluated for accuracy, completeness, citation support and appropriate handling of unanswerable questions.

Phase 8 — Evaluation, polish and demo

  • Measure event precision/recall, link precision/recall, temporal correctness and citation support.
  • Evaluate chat correctness and missing-evidence handling on unseen patient cases.
  • Compare task time and answer accuracy with original reports versus ClinGraph; include source-verification time.
  • Test duplicates, unreadable PDFs, contradictory reports, failed model requests and patient separation.
  • Prepare a repeatable demo that runs live on DeutschlandGPT, the main model. As a safety net only, keep a clearly labelled set of previously saved DeutschlandGPT results to show if the API is unreachable or credits run out during the demo.
  • Report actual results and denominators; do not claim clinical validation from a small synthetic dataset.

Complete when: The complete workflow is reproducible, the evaluation is recorded and the demonstration has a clear evidence-backed story.

Current tooling notes and sources

  • Docling provenance support helps preserve references to original document locations.
  • DeutschlandGPT structured output supports schema-constrained generation (response_format with a JSON schema); factual validation remains necessary. The API ignores seed, so use temperature 0 for consistency.
  • medSpaCy language support currently lists no supplied German ConText or section rules. Treat medSpaCy as optional infrastructure for custom German rules, not ready-made German clinical extraction.

Scope discipline: Start with synthetic data, benchmark model candidates, then use one selected model (DeutschlandGPT claude-sonnet-5) and an explicit processing pipeline. A dedicated graph database, multiple autonomous agents, hospital integrations and production deployment are later decisions. The immediate objective is a reliable, traceable hackathon prototype.
